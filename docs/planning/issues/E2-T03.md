# E2-T03 Highlight the open buffer

Labels: `agent-task`, `epic:editor`, `size:L`, `kind:ui`

## Context
ADR-0009. UI spec editor. Highlight spans use token names, not colours.

## Goal
The open buffer shows syntax colours for the engine E0-T02 selected.

## Scope
Apply spans to the editor component E0-T01 kept. Java at minimum. Other extensions only if ADR-0010 is accepted and the engine supports them; otherwise plain text.

## Out of scope
No language server. No semantic highlighting.

## Design
HighlightScheduler on a single thread, latest-wins, same shape as AnalysisScheduler.
Spans applied on the FX thread in one style pass, not per token.
A highlight failure leaves the previous spans and does not clear the text.
Large-file mode (E2-T09) disables this scheduler.

## Implementation steps
1. Port the winning lexer into ccmm-app.
2. Schedule it from LOCAL edits.
3. Record p95 with highlighting on.

## Acceptance criteria
- Given a Java method, when highlighting finishes, then the keyword span covers `public` and the FX thread did not run the lexer.
- Given a newer edit, when the old job completes, then its spans are not applied.
- Given p95 measured like the keystroke harness, when highlighting is on, then p95 is under 16 ms.

## Tests
HighlighterTest for spans. Keystroke harness appends a row.

## Verification
mvn -B -ntp -pl ccmm-app -am test

## Depends on
E0-T01 go, E0-T02 go, E2-T01.

## Blocks
None.

## Risks and fallbacks
If the bake-off no-gos RichTextFX, restyle against the replacement's API. Do not block the lexer tests on the widget.

## UX spec
Wireframe: docs/design/wireframes/editor.md. Section in docs/design/UI_SPEC.md.
Visuals: tokens only. 900x600 minimum.
Copy: No new strings. Colours are token styles for keyword, string, comment.
Accessibility: icon buttons expose the tooltip as the accessible name. Keyboard shortcuts use Ctrl, and Cmd on macOS via the keymap.

## Evidence required in the PR
Screenshots: dark and light, 100% and 150% scale. A short GIF when the interaction is more than a click. If the change runs on a keystroke, record that the JavaFX thread work stayed inside the 16 ms p95 budget in `docs/benchmarks/keystroke-latency.md` or say why this change does not run on a keystroke.
